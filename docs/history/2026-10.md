## 사진→도면 재실험 — "좌표 보존 ops" 형식이면 게이트웨이 모델도 쓸 만하다 (2026-10-01)

**배경.** 프로젝트 초기 목표 중 하나가 "도면 사진만 올리면 도면을 그려 주는 것"이었다. 2026-08-11
앱 내장 파이프라인(§8 항목18, `docs/ai_image_import.md`)은 결과가 "지저분해서 못 쓴다"는 평가를 받아
2026-08-12 사용자 판단으로 이미지→도면 경로를 통째로 폐기했다(커밋 `3d32606`, 회귀 가드
`test_sketch_pipeline_and_host_ai_modules_removed`). 사용자가 "MCP 서버를 만들어 Claude Code가 앱을
직접 제어하면 어떨까"를 물어, 먼저 MCP 없이 같은 효과(그리고-보고-고치기)를 실험했다.

**실험 1 — Claude Code 세션이 직접.** KBS 1TV 계통도 사진 1장(1252×733,
`docs/reference/sketch_ops_1tv/photo.png`)을 6조각 2배 확대로 읽고, 원본 픽셀 좌표 그대로 상자·글자·
고정 경로 연결선·장식선(안테나·스위치)·1점쇄선 테두리를 스크립트로 적어 `.ecad`를 만들었다
(`session_baseline.py`). 실제 창에 불러 렌더→원본과 비교→겹친 글자 2곳 수정. 상자 18개·포트명·
케이블 번호까지 원본 배치 그대로 나왔다. `sketch_build.Sketch`에는 고정 경로 선·점선 테두리·장식선이
없어 빌더의 `_items`에 dict를 직접 넣는 헬퍼를 썼다(→ `tools/sketch_ops.py`로 정리).

**실험 2 — 같은 과제를 게이트웨이 모델에게.** 실험 1에서 쓴 도형 어휘를 그대로 "ops" JSON 형식
(box·text·line·poly·circle·dashrect, 원본 픽셀 좌표)으로 정의해 프롬프트로 주고(`tools/
sketch_ops_probe.py` `TASK`), 두 방식으로 쟀다. ① oneshot: 원본 1장 → JSON 1회. ② loop: 원본+손으로
고른 2배 확대 조각 6장 → JSON, 이후 [원본+직전 렌더+직전 JSON] → 수정 JSON 2라운드. kairos 계정 키로
실행(사용자 지정). 결과 비교 그림: `docs/reference/sketch_ops_1tv/comparison_gpt6.jpg`·
`comparison_gpt5_sonnet.jpg`. 오류는 렌더를 원본과 눈으로 대조한 것(정량 채점 아님).

| 모델 / 방식 | 결과 | 1회 소요 |
|---|---|---|
| `gpt-5.6-sol` oneshot | 배치·대부분 연결 맞음. 글자 오독·노고 예비 선 끊김 | ~80s |
| `gpt-5.6-sol` loop | 글자 크기·일부 위치 개선, `DVD`·`EDIT OUT`·`예천` 오독과 연결 오류 일부 남음 | ~80s×3 |
| `claude-sonnet-5` oneshot/loop | 위치 밀림·허공에서 끝나는 선·U-LINK 엉뚱. 반복해도 거의 개선 없음. 출력 토큰 ~25k(GPT의 ~4배) | ~250s |
| `gpt-6.1-sol` oneshot | 배치·연결 맞음, 글자 오독 다수(`EX-MFR`·`지향망 (MPEG)`) | ~120s |
| `gpt-6.1-sol` loop | `DWD→DVD` 정도만 남음. 연결선 전부 맞아 보임 | 70~125s×3 |
| `gpt-6-astra` oneshot | 글자 오독 몇 개(`지역망 (M/W)`·`직접 On-Air`) | ~100s |
| `gpt-6-astra` loop | `DVD 200-1` 하나 정도. 노고 주/예비·Bypass 2 경로까지 맞음. 스위치 기호는 세션 기준본보다 원본에 가까움 | 70~95s×3 |

크레딧: 1차(gpt-5.6-sol·sonnet 8호출) 1,657, 2차(gpt-6.1-sol·astra 8호출) 1,558. astra 단가표
(입력 10,000/출력 50,000 per 1M)로 역산하면 2차의 ~1,300이 astra 몫 → `gpt-6.1-sol`은 호출당 ~65
크레딧(추정, 단가 미측정·잔액 차이 역산).

**결론.**
1. 8월 실패의 주원인은 모델이 아니라 **출력 형식**이었다(추정, 사진 1장 표본). 8월은 vision 좌표를
   버리고 관계만으로 재배치(P3.75)했고, 이번엔 원본 좌표·꺾이는 경로·글자를 그대로 적게 했다.
   GPT 계열은 한 번 호출로도 배치·연결 대부분을 맞혔다.
2. 크롭+반복은 주로 **글자 오독**을 고친다(배치는 oneshot에서 이미 대부분 맞음).
3. 추천 조합: `gpt-6.1-sol` + loop — astra와 품질 비슷, 비용 ~1/5.
4. MCP는 이 과제엔 불필요 — 그리고-보고-고치기 루프는 렌더 스크립트만으로 됐다. 막혀 있던 곳은
   "손"이 아니라 "형식"이었다.
5. 같은 모델·같은 입력이라도 실행마다 오독하는 글자가 바뀐다 — 리포 이관 후 `gpt-6.1-sol`
   oneshot 재실행(143s, 출력 7,164토큰)은 배치·연결은 첫 실행과 같았지만 `직장산`·`RF-HRF` 등
   다른 글자를 틀렸다. 글자 정확도는 1회 결과로 판단하지 말 것.
6. 단서: 이 ops 형식은 세션이 한 번 직접 해 본 뒤 만든 것(무엇이 필요한지 아는 지시)이고, 표본이
   사진 1장이다. 다른 도면에서 재시험 필요.

**리포에 남긴 것.** `tools/sketch_ops.py`(ops→.ecad + 원본 프레임 렌더), `tools/sketch_ops_probe.py`
(게이트웨이 실측 재현, 기본 키는 앱과 같은 `resolve_api_key()`, 조각은 기본 3×2 격자 — 이번 실측의
손 조각은 `--crops-json`으로 재현), `docs/reference/sketch_ops_1tv/`(사진·세션 기준본·모델 최종 JSON
2개·비교 그림), 회귀 `test_sketch_ops_spec_roundtrip`. 산출물 폴더 `tools/_sketch_ops/`는 git 무시.

Rejected: MCP 서버로 Claude Code가 앱 직접 제어 | 렌더 스크립트로 같은 반복이 이미 가능했고, 막힌
  곳은 인식 형식이었음
Rejected: claude-sonnet-5(게이트웨이 경유) | 이 과제에서 품질 최하·출력 토큰 ~4배·호출당 ~4분
Confidence: medium
Not-tested: 다른 도면 사진, 오류 정량 채점, gpt-6.1-sol 단가 직접 측정

## 사진→도면 0단계 재시험 — CAD 출력 PDF로 (2026-10-01, 같은 날)

사용자가 준 `1.pdf`(KBS 지역 UHD 송출시스템 UHD-06, A2 1장)로 재시험했다. 파일을 열어 보니 사진이
아니라 **AutoCAD 2022가 직접 낸 벡터 PDF**(이미지 0, 그리기 6,501개, 글자 2,666단어)였다. 그래서 두 갈래로
나눴다(사용자 선택).

**갈래 1 — AI 3종 + 세션 직접, 구획 2곳.** PDF에서 1TV 사진과 비슷한 크기의 구획 2개(UHD SYNC SYSTEM
1253×930, PTP SYNC SYSTEM 1253×621)를 래스터로 잘라 `tools/sketch_ops_probe.py` loop(조각 3×2 자동 격자,
수정 2라운드)로 `gpt-6.1-sol`·`gpt-6-astra`·`claude-opus-5-5`를 돌리고, 이 세션(Opus 5.5)도 같은 ops
형식으로 직접 적었다. **결과: 넷 다 구조(상자·포트·연결·분배기 출력·대각 교차선)를 거의 맞혔다** — 깨끗한
디지털 그림에선 모델 차이가 거의 드러나지 않았다. 차이는 글자 크기 일관성 정도이고, ops 형식에 색이 없어
넷 다 원본의 선 색(초록·하늘·분홍)을 잃었다. 18호출 3,012 크레딧. 출력 토큰은 opus가 GPT의 ~1.6~2배
(sync 9k vs 5.6k). 호출당 27~82초.
→ 이 시험은 "폰 사진"의 일반화 검증으로는 약하다. 1TV 사진에서 어려웠던 건 흐림·기울기·작은 글자였고,
깨끗한 PDF 구획엔 그게 없다. 폰 사진 재시험은 여전히 남는다.

**갈래 2 — AI 없이 PDF 벡터를 좌표째 옮기기.** PyMuPDF `get_drawings()`·`get_text("dict")`로 선·곡선·채움과
글자(위치·크기·색·회전)를 그대로 `.ecad` 아이템으로 바꿨다(`tools/pdf_vector_probe.py`). 도면 전체가
**9,487개 아이템(경로 5,339·채움 다각형 2,726·글자 1,422)으로 약 3초, 크레딧 0**에 원본과 거의 똑같이
옮겨졌다(색 포함). 앱 로드 1.1초. 함정 2개를 겪었다: ① 수평·수직 직선은 둘레 상자 높이/폭이 0이라
`Rect.intersects()`가 거짓 → 구획 필터에서 직선이 통째로 빠짐(0두께 보정). ② AutoCAD는 굵은 선·테두리를
**삼각형 여러 개를 이은 채움 경로**로 낸다 → 하위 경로를 하나로 이으면 검은 삼각형이 생김(끊긴 지점마다
별도 다각형). 한계: 상자는 "상자"가 아니라 선 조각이고 글자도 따로라, DXF 가져오기와 같은 "그림 수준"
편집성이다(상자 단위 이동·지속연결은 안 됨). 9천 개 아이템의 실제 편집 체감(드래그·전체선택)은 미확인 —
성능 문서(`docs/perf_plan_500_1000.md`) 기준 1,000개부터 무거워지는 앱이라 확인 필요.

**결론.** CAD에서 나온 PDF는 AI 경로가 필요 없다 — 벡터 직접 추출이 정확·무료·즉시다(원본 DWG가 있으면
기존 DWG 열기가 더 낫다). AI 경로(§8 항목28)의 존재 이유는 **종이·폰 사진**뿐이고, 그 일반화 검증은 아직이다.

Rejected: PDF 전체를 AI로 | 글자 2,666개라 출력 ~15만 토큰·astra 1회 ~9,000 크레딧(추정), 벡터 추출이 정답을 이미 가짐
Confidence: high(벡터 추출) / medium(구획 AI 비교 — 표본 2개, 눈 대조)
Not-tested: 폰 사진 일반화, 9천 개 아이템 문서의 편집 체감, 벡터 추출의 회전 글자·해치·이미지 포함 PDF

## 사진→도면 0단계 재시험 — 폰 사진(DMB 구획)으로 (2026-10-01, 같은 날)

사용자가 `이미지 모음/`(모악산 송신소 계통도 폰 사진 7장, 5712×4284)에서 하나 골라 해 보라고 했다.
1TV 구획(`IMG_7072`)은 이미 실험 1의 사진이라 빼고, **DMB 구획 `IMG_7074`**를 골랐다 — 처음 보는 구획,
실제 폰 사진(그림자·렌즈 왜곡·약간 기울기), 같은 송신소 계통도라 `TASK` 문구를 바꿀 필요가 없다.
1TV 사진(1252×733)과 비슷한 해상도가 되게 1600×1200으로 줄여 `docs/reference/sketch_ops_dmb/photo.png`에
두고, 인계 지시 그대로 `gpt-6.1-sol` loop(조각 3×2 자동 격자, 수정 2라운드, kairos 키)로 돌렸다.

**결과: 통과(판단 기준 "배치·연결 대부분 맞고 글자 오독 몇 개").** 3호출 114·140·111초, 출력 7.3k~7.9k
토큰, ops 244→280개. 비교 그림 `docs/reference/sketch_ops_dmb/comparison_gpt6.jpg`, 최종 JSON 같은 폴더.
- 맞은 것: 상자 약 20개의 위치·크기, DECODER→TX 교차 연결, 안테나·GPS 기호, 1점쇄선 영역과 그 안의
  Remote Pickup·3dB Coupler·METER·Divider·ACU·D/L, 하단 VDA 삼각형→Encoder→HUB→무선브릿지 경로, 한글
  (`마루이엔지`·`다우비젼`·`무선브릿지`·`송출센터`·`16화면 화상감시`) 대부분.
- 틀린 것: ① **세로로 쓴 케이블 번호**(`<DMBJ1-9>`~`<DMBJ1-14>`, 원본은 선 위에 90° 회전)를 가로로 눕혀
  옆에 몰아 놓아 Multi Viewer 위에서 서로 겹치고, 그 글자가 있던 세로선 구간이 비어 선이 끊겨 보인다.
  ops 형식에 **글자 회전이 없어서** 생긴 것(형식 한계, 인식 문제 아님 — 추정). ② `노고 LINK-2`의
  `EK-MRF/2`를 `EK-MFR/2`로 오독(LINK-1과 같은 글자로 맞춰 버림). ③ `마루이엔지`를 `마루이 엔지`로 띄어 씀.

**결론.** 폰 사진 2장(1TV·DMB)에서 같은 방식이 통했다 — "사진 1장에서만 통한 것"은 아니다(표본 2, 같은
도면의 다른 구획이라 아직 넓은 일반화는 아님). 새로 드러난 개선점은 ops 형식에 `text`의 `rot`(90°) 추가.
§8 항목28 착수 여부는 사용자 결정(8월 폐기 결정을 다시 여는 것).

Confidence: medium(눈 대조, 표본 2)
Not-tested: 다른 종류 도면(전기 단선도·평면도 등), 손그림, 정량 채점, 이번 실행의 크레딧(미측정)

## 0단계 재시험 — DMB 폰 사진으로 모델 4종 비교 (2026-10-01, 같은 날)

사용자가 "3종 비교 아니었나?"라고 물었다. 확인해 보니 sol·astra·opus(API)·세션 비교는 **PDF 구획**에서만 했고,
DMB 폰 사진은 sol만 돌렸었다. 그래서 같은 사진(`docs/reference/sketch_ops_dmb/photo.png`)·같은 조건(loop, 조각
3×2 자동 격자, 수정 2라운드, kairos 키)으로 `gpt-6-astra`·`claude-opus-5-5`를 돌리고, 이 세션(Opus 5.5)도 같은
ops 형식으로 직접 적었다(`session_ops.py`). 단 세션은 눈금자를 그린 3×3 조각(2~3배)을 봤고 수정은 1라운드라
조건이 똑같지는 않다. 비교 그림 `comparison_5way.jpg`(원본·세션·sol·astra·opus), 각 최종 JSON 같은 폴더.

**결과: 넷 다 구조는 거의 같다.** 상자 위치·크기, DECODER→TX 교차 연결, 커플러·스위치·Divider, 하단
VDA→Encoder→HUB→무선브릿지 경로를 모두 맞혔다. 차이는 글자와 세부에서만 났다.
- `EK-MRF/2`(노고 LINK-2): sol만 `EK-MFR/2`로 오독. 세션·astra·opus는 맞음.
- `마루이엔지`: sol만 `마루이 엔지`로 띄어 씀.
- 세로 케이블 번호 `<DMBJ1-9>`~`<DMBJ1-14>`: 넷 다 형식에 회전이 없어 원본처럼 못 그렸다. sol은 한 줄로 눕혀
  Multi Viewer 위에서 겹쳤고, astra·opus는 두 줄(`<DMB`/`J1-9>`)로 쪼개 겹침을 피했고, 세션은 글자를 한 줄에
  하나씩 세웠지만 너무 작아 읽기 어렵다. → `text`의 `rot` 추가가 필요하다는 앞 결론이 그대로 유지된다.
- 출력 토큰: sol 7.3k~7.9k, astra 7.6k~7.9k, opus 19.1k→13.0k→11.2k(첫 호출 기준 GPT의 ~2.5배).

## §8 항목28 1단계 — 형식 정리: 글자 회전(rot)·앞선 참조 연결 (2026-10-01, 같은 날)

사용자가 항목28 착수를 정했다(계획: `docs/EasyCAD_계획.md` §8 항목28). 1단계는 코드 이식 전 형식 정리다.
- **앱 모듈로 이전.** ops→아이템 변환을 `easycad/fileio/photo_ops.py`(`ops_to_sketch`, Qt 비의존)로,

  유지하고 주석만 추가. 전체 1107 통과.

**재실측(sol, DMB, 새 프롬프트, loop 2라운드, 140·128·113초).** 세로 번호 10개 전부에 `rot:90`을 붙였고,

## §8 항목28 2단계 — AI 루프 앱 이식 (2026-10-01, 같은 날)

- **루프 본체** `photo_to_ops.generate_ops(client, photo, model, render, rounds, progress, cancelled, on_round)`
  — Qt 비의존. 수정 라운드의 "직전 결과 렌더"는 `render` 함수로 주입받는다. 수정 라운드 응답이 깨지면 직전
  spec을 유지(로그에 `error`), 첫 생성이 깨지면 ValueError. 취소는 호출 사이에서만(`Cancelled`) — 진행 중인
  HTTP 호출은 못 끊는다.
- **Qt 쪽** 새 파일 `easycad/canvas/photo_dialog.py`(`host_dialogs.py`가 이미 2천 줄대라 분리, 3단계 창도 여기):

  `_PhotoOpsWorker`(QThread). 렌더는 Qt 글자 아이템을 쓰므로 워커가 `BlockingQueuedConnection` 시그널로
  메인 스레드에 맡기고 기다린다. ⚠ 그래서 이 워커를 메인 스레드에서 `wait()`하면 교착 — 테스트도
  `processEvents()` 펌핑으로 기다린다.
- **도구도 같은 루프** — `tools/sketch_ops_probe.py` loop 모드가 `generate_ops`+`render_spec_pil`을 쓴다(앱과 도구

- 회귀 3종(가짜 클라이언트): `test_generate_ops_loop_rounds_render_and_broken_fix`·
  `test_render_spec_qimage_draws_in_photo_frame`·`test_photo_ops_worker_renders_on_main_thread`. 전체 1110 통과.

Confidence: medium — 프록시검증(가짜 응답). 실제 게이트웨이로 앱 경로를 끝까지 도는 건 3단계 창 검증 때.
Not-tested: 실제 게이트웨이 호출(새 루프 경유), 취소 후 창 닫기

## 사진→도면 지시문 범용화 (2026-10-01, 같은 날)

사용자 제안: 방송 계통도가 주용도지만 배포되면 건축 등 다양하게 쓰일 수 있고, 요즘 모델은 제약이 적을 때
더 잘하기도 하니 범용으로. 지시문(`easycad/ai/photo_to_ops.py` `TASK`)을 세 부분으로 나눠 판단했다.
- **뺌 — 분야 문구·예시**: "방송 송신소 계통도", 포트 예시 `THRU1`·`CH1(MW)`, 케이블 번호 `<1DJ1-1>`,

- **유지 — 출력 형식**: ops 어휘·원본 픽셀 좌표·JSON만. 모델을 묶는 제약이 아니라 앱이 결과를 읽는 약속이고,

- **유지(짧게) — 분야 무관 규칙**: 재배치 금지, 지어내지 않기, 글자 빠짐없이 그대로, 세로 글자는 rot.

- 검토한 대안: 모델이 SVG로 바로 출력 — 곡선·빗금까지 되지만 상자-선 지속연결이 사라지고 변경이 커서 보류.
