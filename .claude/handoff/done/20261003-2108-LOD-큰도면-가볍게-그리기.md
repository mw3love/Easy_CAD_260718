# LOD(레벨오브디테일): 큰 도면을 멀리서 볼 땐 대충 그려 가볍게

생성: 2026-10-03 21:08

## 배경

남은 후보 중 4순위(가장 크고 설계 결정이 필요). CLAUDE.md "미해결·보류"의 LOD 항목. 500~1000개 성능 작업
(`docs/perf_plan_500_1000.md`)은 목표 미달로 닫혔고, 남은 격차가 렌더 자체의 바닥값이라 LOD가 필요하다는 결론.
2026-10-03 PDF 가져오기로 9천~58만 개 문서가 현실이 됨: 9,488개 문서에서 전체 선택 6.5초·다시 그리기 1.75초
(`docs/history/2026-10.md` "§8 항목33"), 58만 개는 열기 76초·메모리 약 2.8GB.

## 먼저 할 것

1. 1순위 핸드오프(미니맵 다시 그리기 줄이기)가 끝났다면 그 결과 수치를 기준선으로 쓴다. 안 끝났으면 먼저 그것부터 권할 것.
2. `docs/perf_plan_500_1000.md` 전체(특히 §4 2-D 끝·§7, 1000개 렌더 바닥 142ms·렌더 아닌 몫 77.9ms)와
   `docs/pitfalls.md`의 성능 항목을 읽고, 기존 도구 `tools/perf_bench.py`·`tools/make_perf_doc.py --preset 1000`·
   `tools/perf_baseline_check.py`(기하+시각 지문 회귀 게이트)를 쓴다.
3. 착수 시 deep-interview: 무엇을 얼마나 생략할지(작은 글자·얇은 선·작은 도형을 줌 배율에 따라 숨김/상자로 대체 등),
   목표 수치(예: 1만 개 문서에서 팬·줌·전체 선택 몇 ms), PDF 출력에는 절대 영향 없게(출력은 항상 전체 품질) 같은 제약.
   전체 선택 6.5초는 렌더가 아니라 선택 처리일 수 있어 원인부터 측정으로 나눌 것(짐작 금지).

## 끝 기준(제안 — 인터뷰에서 확정)

정한 목표 수치를 perf 도구로 전/후 실측, 시각 지문 게이트 통과(가까이 보면 그대로), PDF 출력 변화 0, 실제 창에서 1.pdf
수준 문서 팬·줌 체감 확인(손맛은 사용자 몫), 전체 테스트 통과. 큰 작업이라 단계로 나눠 커밋.
